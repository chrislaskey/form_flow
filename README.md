# Form Flow

> Batteries included library for creating dynamic form-based user flows in Phoenix.
> Provides a drop-in web UI to build and renderer. Supports stateful multi-form flows.

## Requirements

FormFlow builds on Phoenix 1.8+ and LiveView 1.1+ (colocated hooks ship the
JavaScript, so there is nothing to `npm install`):

```elixir
{:phoenix_live_view, ">= 1.1.0"},
{:phoenix_html, ">= 4.0.0"},
{:plug, ">= 1.0.0"},
{:ecto, ">= 3.0.0"},
{:ecto_sql, ">= 3.0.0"}
```

An Ecto repo is required: FormFlow stores flow templates and instances in your
application's database. Postgres and SQLite are supported.

## Installation

FormFlow is not yet published to Hex. Add it as a git (or path) dependency in
`mix.exs`:

```elixir
def deps do
  [
    {:form_flow, github: "chrislaskey/form_flow"}
  ]
end
```

[phoenix_select](https://github.com/chrislaskey/phoenix_select),
[dynamic_form](https://github.com/chrislaskey/dynamic_form), and
[slab](https://github.com/chrislaskey/slab) come along as dependencies —
apps never declare them. Each does need its setup registered once, which is
what the rest of this section covers.

### Quick start

Six steps, end to end. Everything below is applied by
[`examples/regenerate.sh`](examples/regenerate.sh), so the demo app is the
executable version of these instructions.

**1. Install the dependency**

```
mix deps.get
```

**2. Point FormFlow at your repo** in `config/config.exs`

FormFlow stores flow templates and instances through your application's repo.
Slab's query mode resolves its own repo the same way:

```elixir
config :form_flow, repo: MyApp.Repo
config :slab, repo: MyApp.Repo
```

**3. Create the database tables**

```
mix form_flow.gen.migration
mix ecto.migrate
```

The generator writes one ordinary Ecto migration into your app that calls into
FormFlow:

```elixir
defmodule MyApp.Repo.Migrations.AddFormFlow do
  use Ecto.Migration

  def up, do: FormFlow.Data.Migration.up(version: 1)
  def down, do: FormFlow.Data.Migration.down(version: 1)
end
```

FormFlow owns the DDL; your app owns when it runs. There is no second migration
command to remember — `mix ecto.migrate`, `mix ecto.rollback`, and your release
migrator all work as they already do.

The version is pinned on purpose: that migration keeps doing what it did when it
was written. **Upgrading FormFlow means running `mix form_flow.gen.migration`
again** to generate a migration for the newer version, which applies only the
steps in between. Re-running `up` on an already-current database is a no-op.

Postgres and SQLite are supported, chosen from your repo's adapter. Postgres
schema prefixes work too — `mix ecto.migrate --prefix` is picked up
automatically, or pass `FormFlow.Data.Migration.up(version: 1, prefix: "tenant")`
explicitly. See `FormFlow.Data.Migration` for other adapters.

**4. Register the colocated hooks** in `assets/js/app.js`

`form_flow`, `slab`, and `phoenix_select` ship their JavaScript as colocated
hooks, extracted at compile time by LiveView 1.1+. There is nothing to install,
but each hook set must be registered once:

```javascript
import {hooks as colocatedHooks} from "phoenix-colocated/my_app"
import {hooks as formFlowHooks} from "phoenix-colocated/form_flow"
import {hooks as slabHooks} from "phoenix-colocated/slab"
import {hooks as phoenixSelectHooks} from "phoenix-colocated/phoenix_select"

const liveSocket = new LiveSocket("/live", Socket, {
  hooks: {...colocatedHooks, ...formFlowHooks, ...slabHooks, ...phoenixSelectHooks},
  // ...
})
```

`dynamic_form` ships no JavaScript, so it has no import here. FormFlow's hook is
the loader for the flow editor — the editor bundle itself is fetched at runtime
rather than bundled, which step 6 covers.

**5. Add the Tailwind sources** in `assets/css/app.css`

Every component renders server-side markup styled with Tailwind, so each
library needs a `@source` line or its classes are never generated:

```css
@source "../../deps/form_flow/lib";
@source "../../deps/slab/lib";
@source "../../deps/dynamic_form/lib";
@source "../../deps/phoenix_select/lib";
```

DynamicForm's built-in components also use [daisyUI](https://daisyui.com)
component classes (`input`, `select`, `checkbox`, `fieldset`, ...). Apps
generated by `phx.new` 1.8+ vendor daisyUI already, so there is nothing to do.
Apps without it can either vendor it the way `phx.new` 1.8 does, or replace
DynamicForm's markup with their own components module — see
[DynamicForm's styling guide](https://github.com/chrislaskey/dynamic_form/blob/main/guides/styling.md).

Using Tailwind v3? Add the same four paths to `content` in
`assets/tailwind.config.js` as `"../deps/<library>/lib/**/*.ex"` instead.

**6. Mount the UI**

FormFlow ships an optional path-based router that dispatches to its
LiveComponents, so one route covers the whole UI:

```elixir
scope "/", MyAppWeb do
  pipe_through :browser

  live "/flows/*path", FlowsLive
end
```

```heex
<FormFlow.Web.router type="templates" path={@path} />
```

The `*path` glob hands your LiveView a list of segments, while the router
takes a path string — join them in `mount/3` or `handle_params/3`:

```elixir
def mount(%{"path" => segments}, _session, socket) do
  {:ok, assign(socket, :path, "/" <> Enum.join(segments, "/"))}
end
```

Apps that would rather own their routing can skip the router and call the
LiveComponents directly.

**Serving the flow editor.** The visual flow builder is React and ReactFlow —
~390 KB. FormFlow does not put that in your `app.js`, where every page in your
app would pay for it. Instead the bundle is prebuilt, shipped inside the
package, and fetched at runtime by the colocated hook you registered in step 4,
so only pages that actually render the builder download it. Declare the route it
is served from, outside any pipeline and **before any catch-all route**:

```elixir
import FormFlow.Web.Assets.Router

scope "/" do
  form_flow_assets()
end
```

That is the entire integration: no npm, no `package.json`, and no changes to
your esbuild, vite, or webpack configuration — the bundle never passes through
your bundler. The path carries a content hash and is served
`immutable`, so it caches forever and needs no `mix phx.digest`.

Mounting somewhere other than `/form-flow`? Configure it once; the route and the
URL the hook fetches both derive from this, so they cannot drift:

```elixir
config :form_flow, asset_path: "/assets/form-flow"
```

### Optional: file uploads

DynamicForm's `type="file"` questions upload directly to cloud storage using
presigned URLs, which needs a presigner module plus a JavaScript uploader
registered on the socket:

```javascript
const GoogleStorage = (entries, onViewError) => {
  entries.forEach(entry => {
    // PUT the file to entry.meta.url, calling entry.progress(percent)
  })
}

const liveSocket = new LiveSocket("/live", Socket, {
  uploaders: {GoogleStorage},
  // ...
})
```

See [DynamicForm: file uploads](https://github.com/chrislaskey/dynamic_form/blob/main/guides/usage.md#file-uploads).

### Optional: translated validation errors

DynamicForm translates validation errors through Gettext, defaulting to its
own backend. Apps with their own translations pass their backend to the form.
See [DynamicForm: internationalization](https://github.com/chrislaskey/dynamic_form/blob/main/guides/usage.md#internationalization).

## Demo app

The `examples/` directory contains a full Phoenix app wired up exactly as
described above:

```
cd examples/demo
mix setup
mix phx.server
```

Then open [http://localhost:4000](http://localhost:4000). The `/install-check`
page renders one component from each dependency, so a missing hook, Tailwind
source, or daisyUI shows up immediately. See
[examples/README.md](examples/README.md).
